# 弱网优化策略（Android）

> **一句话定位**：弱网优化的本质不是"让网变快"，而是"在不可靠的网络上给用户确定性与可预期性"。
>
> 网络快慢你控制不了，但"多久给反馈、失败了怎么兜底、数据旧到什么程度、什么时候取消"这些是客户端能控制的。本文按"原理 → 分层策略 → 场景 → 度量 → 坑 → 追问"组织，代码是 Kotlin，注释中文。

---

## 一、先搞清"弱网"到底弱在哪（原理）

弱网不是一个指标，是一堆现象。优化前必须先把它拆开，否则会出现"明明加了重试，还是卡"这种情况。

### 1.1 影响链路分层拆解

| 环节 | 弱网下会发生什么 | 后果 |
| --- | --- | --- |
| DNS 解析 | 解析慢、超时、被运营商劫持到错误 IP | 请求还没发出去就等了几百毫秒到几秒，甚至直接失败 |
| TCP 三次握手 | 每建一次连接就多一个 RTT | 建连本身就要花掉一个往返时间 |
| TLS 握手 | 完整握手要多几个 RTT；会话票据过期后要重来 | 短请求里"握手时间"可能比传数据还长 |
| 丢包与重传 | 丢一个包就要等超时重传，TCP 还会因此降速 | 队头阻塞：一个包丢了，后面到达的数据也用不上 |
| 带宽抖动 | 可用带宽忽高忽低 | 大响应下载到一半变慢；媒体卡顿、码率切换 |
| 高 RTT | 海外跨洲往返常在 200~500ms 量级（量级参考，实际看链路） | 每个 RTT 都在累积；串行请求越多越慢 |
| 连接被静默回收 | 运营商/NAT 网关回收长时间无数据的空闲连接 | 客户端以为连接还在，发出去才知道已死，白等一次超时 |
| **App 侧自身问题** | 请求过多、无优先级、无去重、无缓存、超时设置不合理 | **这类问题在"好网"下看不出，弱网下会成倍放大** |

**结论先给**：弱网下暴露出来的问题，一大半是 App 自己造的。网络链路是外因，请求设计是内因，内因往往更容易改、收益也更大。

### 1.2 "用户感知 vs 真实原因"对照表

用户不会说"DNS 慢"，他只会说"点不动"。排查时要往下挖到真实原因：

| 用户感知 | 常见真实原因 |
| --- | --- |
| "点了一下没反应" | 首字节等待期间无任何 UI 反馈（缺骨架屏/进度） |
| "要转好久圈" | 多接口串行、无并发、TLS 握手每次都重来 |
| "刷出来是空白" | 把"请求失败"当成了"没有数据"渲染成空态 |
| "怎么又变回旧的了" | 缓存没有版本/TTL 校验，脏数据覆盖新数据 |
| "点了两次点赞，多了一个" | 重试没有幂等，重复提交 |
| "看着像卡死" | 超时设置过长，客户端在死等一个永远不会来的响应 |
| "流量怎么这么多" | 预加载抢带宽、弱网下自动播放视频、埋点即时上报 |
| "返回上一步又要重新加载" | 只优化了首屏，没做返回栈的数据复用 |

## 二、优化策略清单（按层次分）

每个策略都给三样东西：**做法 / 原理 / 代价与风险**。没有银弹，任何优化都有代价。

### 2.1 连接层

连接层优化的核心目标：**少建连、少握手、少被打断。**

| 策略 | 做法 | 原理 | 代价/风险 |
| --- | --- | --- | --- |
| HTTP/2 多路复用 + 连接池 | 复用同一个 OkHttpClient（全局单例），让请求共享连接 | HTTP/2 在一条连接上多路复用，省掉反复建连和握手；连接池复用已建立的连接 | 单连接上的 TCP 队头阻塞仍在（H2 解决的是应用层队头阻塞，不是 TCP 的）；长连接需处理服务端主动断开 |
| HTTP/3（QUIC） | 服务端支持时开启 QUIC | QUIC 基于 UDP，丢包只影响受影响的流，不同流之间不互相阻塞；连接迁移（切 Wi-Fi/4G）靠连接 ID 保持，不用重建 | 需服务端/CDN 支持；企业网络可能封 UDP；不保证一定更快 |
| TLS 1.3 与会话复用 | 用支持 TLS 1.3 的运行时；开启会话票据/会话恢复 | TLS 1.3 握手轮次比 1.2 少；会话复用让重连时省掉完整握手 | 老设备/老服务端可能不支持；会话票据有效期到期后仍要完整握手 |
| DNS 优化 | HTTPDNS 或 DoH；对关键域名做本地预解析并缓存结果 | 绕开运营商 DNS 的解析慢/劫持；提前解析省掉"请求前先等解析" | HTTPDNS 需额外请求且要兜底系统 DNS；预解析失败要能回退，不能阻塞主流程 |
| CDN 就近接入 | 静态资源、图片、媒体走 CDN，按地域就近调度 | 缩短物理距离 = 降低 RTT | 配置与调度质量依赖服务商；缓存刷新有延迟 |
| 多域名并发 | 用多个域名分摊并发下载（合理数量，如 2~4 个，经验取值） | 浏览器/客户端对单域名并发有限制，多域名可提升并行度 | 域名过多会带来更多 DNS 解析和建连开销，反而更慢（过度并发是坑） |
| 连接预热 | 进入页面/应用启动时对即将用到的域名提前建连 | 提前把握手成本花在"用户还没点"的时候 | 预热了不一定会用到，浪费资源；要控制预热的域名数量和时机 |

### 2.2 请求层

请求层优化的核心目标：**该发的才发、只发一次、发出去能取消。**

| 策略 | 做法 | 原理 | 代价/风险 |
| --- | --- | --- | --- |
| 请求合并 / 批量接口 | 把 N 个小请求合成一个批量接口（如批量详情、批量状态） | 减少请求数量 = 减少建连、TLS、头部开销和 RTT 累积 | 服务端要支持；批量的失败会"连坐"，需要部分成功语义 |
| 请求去重 | 同一资源并发拉取时，只发一次，其余订阅同一结果 | 避免同一份数据被并发重复请求，弱网下尤其致命 | 需要一个"in-flight 请求表"，请求返回后要正确清理 |
| 优先级与取消 | 不可见内容、离开页面立即取消；给关键请求更高优先级 | 把有限带宽给用户当前真正看的东西 | 取消逻辑要成对，取消后要处理回调，避免状态错乱 |
| 超时分级 | 连接、读、写分别设置超时，不要全局一个值 | 不同阶段合理耗时不同：连不上要快速失败，读大文件要久一点 | 值要靠数据调；过短误杀慢但正常的请求，过长会让用户干等 |
| 重试策略 | 指数退避 + 随机抖动 + 幂等保证 + 最大次数（如 3 次，经验取值） | 退避避免打垮服务端，抖动避免全量客户端同时重试，幂等避免重复副作用 | 非幂等接口不能盲重试；要区分可重试错误（网络/5xx）和不可重试（4xx 参数错） |
| 失败降级 | 走缓存 / 占位图 / 兜底数据，而不是空白或崩溃 | 弱网下"有旧的可看"优于"什么都没有" | 降级数据可能过期，要明确标注；不能把降级当成正常结果 |
| 乐观更新与本地先行 | 点赞、发送等操作先在本地改 UI，再异步同步 | 用户操作立即有反馈，感知不依赖网络 | 需要回滚机制（同步失败要还原 UI）；要配合幂等防止重复 |

**重试的一种常见写法（指数退避 + 抖动）：**

```kotlin
/**
 * 计算第 attempt 次重试的等待时间（毫秒）。
 * base 是基础间隔，cap 是单次等待上限，抖动范围 ±30%。
 * 这些具体数值都是经验取值，实际要按业务和服务端能力调整。
 */
fun backoffMillis(attempt: Int, base: Long = 500L, cap: Long = 30_000L): Long {
    // 指数：base * 2^(attempt-1)，并封顶
    val exp = (base * (1L shl (attempt - 1))).coerceAtMost(cap)
    // 抖动：在 exp 的 ±30% 之间随机，避免重试风暴同时发生
    val jitter = (exp * 0.3).toLong()
    return exp + (-jitter..jitter).random()
}

/** 只对可重试的错误做退避重试；4xx 这类直接失败，不浪费用户时间 */
suspend fun <T> retryWithBackoff(
    maxAttempts: Int = 3,
    isRetryable: (Throwable) -> Boolean = { it is java.io.IOException },
    block: suspend () -> T
): T {
    var attempt = 1
    while (true) {
        try {
            return block()
        } catch (e: Throwable) {
            if (attempt >= maxAttempts || !isRetryable(e)) throw e
            delay(backoffMillis(attempt))
            attempt++
        }
    }
}
```

### 2.3 数据层

数据层优化的核心目标：**传得更少、拿得更准、存得更久。**

| 策略 | 做法 | 原理 | 代价/风险 |
| --- | --- | --- | --- |
| 增量同步 | 用游标（cursor）/序号（seq）只拉自上次以来的增量 | 传的数据量和耗时与"变化量"成正比，而不是"总量" | 需要服务端支持游标；游标丢失时要能全量兜底 |
| 协议瘦身 | 用 Protobuf 替代 JSON；JSON 下做字段裁剪，只取需要的字段 | 二进制编码体积更小、解析更快；字段裁剪直接减少字节数 | Protobuf 调试不如 JSON 直观；字段裁剪要维护多套 schema |
| 压缩 | 响应走 gzip/br，请求体也压缩 | 减少传输字节数，弱网带宽抖动时收益明显 | 压缩/解压耗 CPU；已压缩过的内容（图片/视频）再压缩没意义 |
| 本地缓存 | HTTP 缓存语义（Cache-Control/ETag）+ 本地数据库（如 Room）+ 内存 LRU | 命中缓存就完全不需要走网络；条件请求用 304 省流量 | 缓存一致性最难：要有版本与 TTL，否则脏数据；内存缓存要控制上限 |
| 分页与预加载 | 拉一页播一页、进入即预取下一页 | 首屏数据量小 = 首屏快；提前拉减少用户等待 | 预加载抢首屏带宽（坑）；预取过多浪费流量 |
| TTL 与失效策略 | 每类数据设合理 TTL；写入后主动失效相关缓存 | 已过期数据不返回给用户，避免展示过期信息 | TTL 太短命中率低，太长又不实时，需要按数据类型分别设 |
| 批量上报 / 合并上报 | 埋点、日志先本地攒着，定时或攒够一批再上报 | 减少请求数量，弱网下尤其重要 | 攒着就有丢失风险（进程被杀），要有落盘和补报机制 |

**缓存示例（OkHttp 磁盘缓存 + 条件请求）：**

```kotlin
// 磁盘缓存：弱网下"能命中缓存"是最直接的优化
val cache = Cache(
    directory = File(context.cacheDir, "http_cache"),
    maxSize = 50L * 1024 * 1024   // 50MB，经验取值
)

val client = OkHttpClient.Builder()
    .cache(cache)
    .connectTimeout(5, TimeUnit.SECONDS)   // 连不上要快速失败，别让用户干等
    .readTimeout(15, TimeUnit.SECONDS)     // 读可以给长一点，大响应需要时间
    .retryOnConnectionFailure(true)        // OkHttp 内置连接层重试
    .build()
```

服务端配好 `Cache-Control`、`ETag` / `Last-Modified` 后，OkHttp 会自动处理缓存和 304，客户端不用自己写缓存逻辑。

### 2.4 媒体层

媒体层优化的核心目标：**在带宽不确定的情况下，保证"先能看"，再谈"看得清"。**

| 策略 | 做法 | 原理 | 代价/风险 |
| --- | --- | --- | --- |
| 多码率自适应（HLS/DASH） | 服务端转多档码率，客户端按带宽估计切档 | 带宽好时高清、带宽差时自动降码率，避免卡死 | 需要转码和存储成本；切换点要平滑，切太频繁会抖动 |
| 图片按展示尺寸请求 | 按控件实际尺寸请求对应分辨率的图，别总拉原图 | 一张 200px 的缩略图不需要 2000px 的原图 | 需要图片服务支持尺寸参数；尺寸变了要重新请求 |
| 图片格式选择 | 优先 WebP，支持时用 AVIF | 同等画质下体积更小 | 老设备可能不支持，需要按能力降级 |
| 渐进式加载与模糊占位 | 先显示模糊小图/主色块占位，再替换清晰图 | 用户先看到"内容在那儿"，感知等待变短 | 需要额外生成占位数据；占位处理不好会有明显闪动 |
| 视频预缓冲与首帧优先 | 提前缓冲当前可见视频的前几秒；优先保证首帧 | 首帧上屏是用户"开始播了"的判定标准 | 预缓冲抢带宽；多视频同时预缓冲会争抢资源 |
| 大文件断点续传 | 分块下载 + HTTP Range 请求，记录已下载偏移 | 中断后从断点继续，不从头再来 | 服务端要支持 Range；分块元数据要落盘 |
| 上传分片与并发控制 | 大文件切片上传，失败只重传失败分片；控制并发数 | 单片失败不必重传整文件；并发过高会拖垮上行带宽 | 需要分片合并和服务端支持；并发数要限（一般 1~3 个，经验取值） |

### 2.5 状态层

状态层优化的核心目标：**知道自己在什么网络里，并据此改变行为。**

| 策略 | 做法 | 原理 | 代价/风险 |
| --- | --- | --- | --- |
| 网络质量探测与分级 | 结合带宽估计与 RTT，把网络判成"好/一般/差" | 后面所有策略都要依赖这个判断，它是决策入口 | 探测本身有成本；判据不准会导致策略选错 |
| 按质量动态调整 | 差网络降清晰度、减少预加载、关闭自动播放 | 把有限带宽优先给"用户主动要的内容" | 降级要平滑，突然变糊会让人以为出 bug |
| 离线队列 | WorkManager 持久化任务 + 去重 + 顺序 + 失败重试 | 提交类操作先落本地队列，联网后再执行，保证不丢 | 需要幂等（防重复）+ 排序（防乱序），实现复杂度高 |
| UI 反馈 | 骨架屏、进度、可重试的错误态 | 让用户知道"在加载"“失败了能重试”，而不是怀疑卡死 | 要区分加载中/空结果/错误三种态（坑：把失败当无数据） |

**Android 上判断网络状态的粗粒度方式（注意：只能判"有没有网"，判不了"好不好"）：**

```kotlin
// 用 ConnectivityManager 拿到的可用性，只能做粗判断
val cm = context.getSystemService(ConnectivityManager::class.java)
val caps = cm.getNetworkCapabilities(cm.activeNetwork)
val hasInternet = caps?.hasCapability(NetworkCapabilities.NET_CAPABILITY_VALIDATED) == true
// 强弱网要靠实测：请求耗时、RTT、带宽估计（如 OkHttp 的 EventListener 统计）
// Android 提供的 bandwidth 估计并非所有 API 级别都可用，且精度有限，需自行兜底
```

**离线队列示例（WorkManager 落盘 + 幂等键去重）：**

```kotlin
// 提交类操作（点赞/发帖）：先写本地，再入队，联网后执行
class SubmitWorker(
    appContext: Context,
    params: WorkerParameters
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result {
        val payload = inputData.getString("payload") ?: return Result.failure()
        return try {
            api.submit(payload)          // 接口必须幂等（携带客户端生成的唯一 id）
            Result.success()
        } catch (e: IOException) {
            Result.retry()               // 交给 WorkManager 按退避策略重试
        }
    }
}

// 入队：用唯一名 + ExistingWorkPolicy 保证同一操作不会重复入队
val request = OneTimeWorkRequestBuilder<SubmitWorker>()
    .setInputData(workDataOf("payload" to json))
    .setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)   // 有网才跑
            .build()
    )
    .setBackoffCriteria(
        BackoffPolicy.EXPONENTIAL,
        10, TimeUnit.SECONDS     // 指数退避（WorkManager 自带，但抖动需自己控制粒度）
    )
    .build()
WorkManager.getInstance(context).enqueueUniqueWork(
    "submit_${payloadId}",                 // 唯一名 = 幂等键，天然去重
    ExistingWorkPolicy.KEEP,               // 已存在就不重复入队
    request
)
```

## 三、典型场景怎么做

单纯记策略没用，面试要的是"这个场景你怎么组合"。下面每条给"弱网下具体动作"。

| 场景 | 弱网下的具体动作 |
| --- | --- |
| **Feed 首屏** | 只请求首屏需要的字段（协议瘦身）；命中本地缓存先渲染旧内容，再后台刷新；首屏请求优先、其余延后；骨架屏立即上屏，别等数据 |
| **图片列表** | 按控件尺寸请求缩略图；模糊占位 + 渐进加载；快速滑动时取消已滑出项的请求；预取范围按网络质量动态调整（差网少预取） |
| **短视频起播** | 优先保证首帧：先拉低码率起播，再按带宽切档；弱网降清晰度、减少预缓冲条数；不在不可见时预加载；弱网下关闭自动播放省流量 |
| **IM 消息收发与补拉** | 发送走离线队列 + 幂等 id；收到消息带 seq，本地去重排序；断线重连后按本地最大 seq 补拉增量；重连用指数退避 + 抖动；区分"服务器确认已发"和"本地已显示" |
| **提交类操作（点赞/发帖/支付）** | 必须幂等：客户端生成唯一请求 id，服务端去重；乐观更新先改 UI，失败回滚；用持久化队列保证不丢；支付这类不能盲目重试，要查单确认 |
| **埋点上报** | 本地攒批，定时/攒够一批再上报；带上时间戳和唯一 id 支持服务端去重；弱网下降低上报频率；落盘防进程被杀丢失 |
| **文件上传下载** | 分块 + 断点续传；上传错误只重传失败分片；控制并发（1~3，经验取值）；进度可暂停/继续；失败可手动重试，不要静默失败 |

## 四、怎么量化与验证

**没有度量就没有优化。** 先定指标，再改代码，否则你不知道改完是变好还是变坏。

### 4.1 核心指标定义

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| TTFB（首字节时间） | 发出请求到收到第一个响应字节的时间 | 反映服务端 + 链路延迟，不含下载体 |
| 请求成功率 | 成功请求数 / 总请求数 | 要区分"业务失败"和"网络失败" |
| P95 / P99 耗时 | 95 / 99 分位的请求耗时 | 平均值会掩盖长尾，弱网下的糟糕体验全在分位里 |
| 重试率 | 发生过重试的请求占比 | 重试率高说明失败多或超时设置不合理 |
| 缓存命中率 | 命中缓存的请求 / 总请求 | 命中率高直接减少网络请求 |
| 每用户流量 | 单位时间/每会话的用户流量 | 弱网地区用户对流量敏感，要监控 |
| 卡顿率（媒体） | 播放中 buffer 次数 / 播放时长 | 衡量媒体流畅度的关键指标 |

### 4.2 埋点要分阶段

一个请求要拆成多段计时，才能知道慢在哪：

```
请求发出 → DNS 解析 → TCP 连接 → TLS 握手 → 发出请求 → 收到首字节(TTFB) → 下载响应体 → 解析完成
```

OkHttp 的 `EventListener` 能拿到 DNS、连接、TLS、请求、响应各阶段的耗时，是分阶段埋点的标准做法；媒体播放则用 `AnalyticsListener` 的 `onLoadStarted` / `onLoadCompleted` / `onRenderedFirstFrame`（首帧）。

```kotlin
// OkHttp EventListener：分阶段埋点，定位"慢在握手还是慢在首字节"
class TimingEventListener : EventListener() {
    private var callStart = 0L
    private var dnsStart = 0L
    private var connectStart = 0L

    override fun callStart(call: Call) {
        callStart = System.nanoTime()
    }
    override fun dnsStart(call: Call, domainName: String) {
        dnsStart = System.nanoTime()
    }
    override fun dnsEnd(call: Call, domainName: String, addresses: List<InetAddress>) {
        // 上报：DNS 耗时 = now - dnsStart
    }
    override fun connectStart(call: Call, inetSocketAddress: InetSocketAddress, proxy: Proxy) {
        connectStart = System.nanoTime()
    }
    override fun connectEnd(call: Call, inetSocketAddress: InetSocketAddress, proxy: Proxy, protocol: Protocol?) {
        // 上报：TCP 连接耗时 = now - connectStart
    }
    override fun callEnd(call: Call) {
        // 上报：总耗时 = now - callStart
    }
}
```

### 4.3 怎么模拟弱网

验证弱网优化，首先得能造出弱网。工具有：

| 方式 | 说明 |
| --- | --- |
| Android 模拟器 | 内置网络限速设置，可设定速率、延迟、丢包（模拟器面板里的网络设置） |
| Charles / 抓包工具 | 可设限速（Throttle）模拟不同带宽与延迟，顺带看请求内容 |
| Network Link Conditioner | macOS 上的网络条件模拟工具，可加延迟与丢包 |
| Linux `tc` + `netem` | 在服务端/网关上注入延迟、丢包、乱序，最接近真实链路 |
| 真机 + 弱网国家节点 | 连真实海外节点（如东南亚、南美）测试，最能反映真实跨洲 RTT |

建议组合：**开发期用模拟器/Charles 快速验证，上线前用真实弱网节点跑一遍分阶段埋点。**

## 五、常见坑

| 坑 | 说明 | 正确做法 |
| --- | --- | --- |
| 无脑重试导致雪崩 | 服务端一抖，全量客户端同时重试，把它彻底打挂 | 指数退避 + 随机抖动 + 最大次数 + 熔断 |
| 重试没有幂等导致重复提交 | 重试把一次点赞变成两次，把一次支付变成两笔 | 客户端生成唯一请求 id，服务端按 id 去重 |
| 超时过长 / 过短 | 过长用户干等，过短误杀慢但正常的请求 | 分阶段设超时，用数据调，不要一个值走天下 |
| 离线队列不去重不排序 | 队列里同一操作入队多次，或后发先至导致状态错乱 | 唯一键去重 + 需要顺序的场景用串行队列 |
| 缓存没有版本与 TTL | 旧数据覆盖新数据，或永远显示过期内容 | 每条缓存带版本号 + TTL + 主动失效 |
| 并发请求过多争抢带宽 | 几十个请求同时发，每个都很慢 | 限并发数，分优先级，非关键请求排队 |
| 把"失败"当"无数据" | 请求失败渲染成空列表，用户以为真没有内容 | 区分"空结果 / 加载中 / 错误"三种状态，错误态可重试 |
| 只优化首屏不优化返回 | 首屏很快，返回上一页又重新加载一遍 | 返回栈复用已有数据，从缓存渲染 |
| 预加载抢首屏带宽 | 预取下一页把首屏请求挤慢 | 首屏最高优先级，预加载延后或按网络质量决定 |
| 弱网下自动播放视频 | 用户没点就开始播，流量哗哗走 | 弱网/移动网络下默认不自动播放，或只在可交互后播 |
| 后台任务在 Doze 下被延迟 | 重试和上报在低电耗模式下被系统推迟 | 用 WorkManager 接受系统调度，设计成"可延迟不丢" |

## 六、面试追问速答

**Q：弱网下你会最先改哪三件事？**
先看数据找出最慢/失败最多的一段，通常优先做三件：一是**缓存与本地优先**，让用户先看到旧数据而不是空白；二是**超时与重试分级**，让失败快速暴露、可重试的才重试；三是**减少和合并请求**，把不必要的小请求砍掉或合并。前两件保证"确定性和可预期性"，第三件直接减少弱网下的失败面。如果做媒体，还要加上"首帧优先 + 按带宽降档"。

**Q：怎么区分是客户端、网络还是服务端问题？**
靠分阶段埋点和对照实验。如果请求根本没发出去（DNS 或建连就超时），是网络/客户端；如果发出了、服务端收到并记录了耗时，但客户端很晚才拿到，多半是链路或响应体太大；如果服务端自己处理就慢，是服务端。再看分布：特定地域、特定运营商慢 → 网络/CDN；所有地域都慢 → 服务端；只有某些机型慢 → 客户端（解析、压缩、渲染）。最后用同一接口在好网下复测做对照。

**Q：离线提交怎么保证不重复也不丢？**
不丢靠"先落本地再入队"：用户操作立刻写本地数据库和持久化队列（WorkManager），进程被杀也不丢。不重靠幂等：客户端为每个操作生成唯一请求 id（比如 UUID），随请求发给服务端，服务端按 id 去重，重复到达只处理一次。顺序靠队列：需要保序的操作串行执行。三者组合就是"持久化 + 幂等键 + 有序队列"，缺一个都会出问题。

**Q：请求去重和幂等有什么区别？**
去重是**客户端侧、针对并发**的优化：同一资源正在请求时，后来的请求不重复发，共享同一个结果，目的是省流量和减轻服务端压力。幂等是**服务端侧、针对重复执行**的保证：同一个请求执行一次和执行多次，结果一样，目的是防止重试/乱序造成重复副作用。去重是"尽量少发"，幂等是"多发也不怕"。网络不可靠，重试必然会重复到达，所以幂等是安全底线，去重只是性能优化。

**Q：QUIC/HTTP3 在弱网下为什么更好？**
两点最实在。一是**消除队头阻塞**：HTTP/2 虽然多路复用，但底层还是 TCP，一个包丢了后面所有流都得等重传；QUIC 在 UDP 上实现，各流独立，一个流丢包不影响其他流。二是**连接迁移**：QUIC 用连接 ID 而非四元组标识连接，用户从 Wi-Fi 切到 4G 时连接不断，不用重建和重新握手，省掉一个完整握手的时间。此外 QUIC 默认加密、握手轮次更少也顺带受益。前提是服务端和网络都支持 UDP。

**Q：为什么重试要加抖动？**
因为重试如果都用相同的退避时间，服务端一抖动，所有客户端会在同一时刻集体重试（这就是重试风暴/惊群），把本已脆弱的服务端再次打挂，然后进入"失败—重试—再失败"的恶性循环。加随机抖动把重试时间打散，让负载在时间上摊平，服务端有机会恢复。公式上的表现就是"退避时间 ±一定比例随机"，而不是固定值。抖动是分布式系统里保护服务端的基本手段。

**Q：怎么衡量弱网优化的收益？**
用分层指标做前后对比，且必须在**同一弱网条件下**比。核心看：P95/P99 耗时（平均没用）、请求成功率、重试率、缓存命中率、每用户流量、媒体的卡顿率和首帧时间。做法是先在弱网模拟环境里跑一遍基线，改完再跑同样的场景，看这些指标的变化。注意收益要落到用户感知上：首屏时间、可交互时间、错误率这些才是用户真正感受到的，服务端指标只是中间过程。

## 七、面试口述版

> "弱网优化不是把网变快，网络快慢我们控制不了，我们能控制的是在不可靠网络下给用户确定性和可预期性。做法上分五层：连接层少建连少握手，用 HTTP/2 复用、HTTP/3、TLS 1.3、HTTPDNS；请求层减少数量、去重、可取消、超时分段、重试要退避加抖动加幂等；数据层用增量同步、协议瘦身、本地缓存和批量上报；媒体层做自适应码率、按尺寸请求图片、首帧优先、断点续传；状态层做网络质量分级、按质量调策略、离线队列和明确 UI 反馈。所有优化都要先度量，用分阶段埋点看慢在哪，用弱网模拟环境验证收益。最容易踩的坑是无脑重试导致雪崩、没有幂等导致重复提交、缓存没版本导致脏数据、以及把失败当无数据。"
